# Batch A review r2 (Opus, Codex stand-in), 2026-10-15

Range `b768e6339..b40023eac` in `~/Claude/Projects/NuvioMobile-rc3-a` (branch `claude/steven-rc3-a`), MPVKit excluded, with the round-1 fix commit `b40023eac` read hunk by hunk. Read-only; nothing built or run. Tally: **0 P1 / 5 P2 / 6 P3.**

## Findings

1. **P2 (new in the fix): a forced-card request is never cleared after it lands, so it outlives the restore and can steal focus later.** `Screens/HomeView.swift:2386-2400` with `:2009-2040` and `PinnedRowUpFallback.swift:121-138, 171-181`. The forced rung only runs when the origin row already owns focus. When it lands, focus moves card to card inside that row, so `.onChange(of: focus.wrappedValue != nil)` does not fire (true → true), `handleRowFocusOwnership` is never called, and neither `endUpFallback` nor the "`rowFocusRequest.rowKey == rowKey` → `.none`" line clears it. Rung 2 then logs `landed=1` and bumps `returnGeneration`, which also disarms the 1.0 s expiry closure (its generation guard returns early). The request `{origin row, wanted, forceCard: true}` stays in the environment until some other row claims focus. Failing scenario: the forced rung lands. The viewer presses Up into the hero CTA (no row claim change, nothing clears it), opens Detail from the CTA (`notePush` records no origin) and presses Back. `restoreRowAfterPop` returns early, but the row's `.onAppear { applyIfMatching(request) }` (F5) runs again as Home's root reappears. The row's focus is nil there, so it writes `wanted` and pulls focus off the CTA the engine just restored. That is the case the BUG-156 code says it never does ("a row request there would steal it"). A milder version: Right to another card in the same row, open it, Back. The old forced request re-applies on appear before rung 1 and focus flicks to the old card until rung 1/2 forces it back. **Fix:** clear the request whenever a restore ends: in the `landed=1` branch and in the press-cancel branch, `if rowFocusRequest.rowKey == origin.rowKey, activeUpFallbackTarget == nil { rowFocusRequest = .none }`. Better still, clear it in `noteFocusedItem` when `(rowKey, itemId)` equals the live request's `(rowKey, itemId)`, so it clears at the moment the forced write lands.

2. **P2: a forced request can name a card that is no longer in the row, and it is now written into a row that HOLDS focus.** `PinnedRowUpFallback.swift:46-51` (`target` returns `r.itemId ?? remembered ?? firstId` without checking that the row contains the id) and `:178-180` (the new forced guard). Before the fix, a stale `itemId` only reached a row whose focus was nil, so writing an id no view carries was a no-op and rung 3 (`forceFirst`) recovered. Now `focus.wrappedValue != target` is always true for a stale id, so the forced write replaces a focused card with a value that matches no view. That is the BUG-47 class: SwiftUI either drops the row's focus (the engine then falls to its default or nowhere until rung 3, and a press in that window retires rung 3 through `returnPending`) or ignores the write. This happens a lot on Continue Watching: open Detail from a CW card (hold menu → Go to Details), play the episode and come back. The CW entry's `videoId` is now the next episode, and CW reorders. The engine restores CW on some card, and rungs 1 and 2 force the old `videoId`. Catalog reloads, Upcoming and library-backed rows can do the same. **Fix:** only force when the row contains the card. Either the rung checks `wanted` against the origin row's current ids (Home has the row models: CW `entries`, `section.items`, folder ids, the See All key), or `applyIfMatching` gets the row's id set (or a `contains` closure) beside `firstId` and declines a forced target outside it. Add a unit case for `target` with a stale id.

3. **P2 (round-1 P2-3, partly fixed): the forced rung only runs if the engine restores focus before 0.3 s, and on tvOS it most likely restores at the end of the pop transition, after rung 2.** `HomeView.swift:2383-2394`, `HomeReturnFocusMemory.isLastRung` (`:7149`). `homePath.count → 0` fires at the start of the pop. The row's focus was released at the push (that is what `releaseGrace` covers), so at rung 1 (t≈0) and usually at rung 2 (0.3 s) `focusedRowKey` is nil. Those rungs send ordinary requests, and those requests can be dropped while the root is still mid-transition. If the engine's own restore then lands in the right row on the wrong card at about 0.45 to 0.5 s, the claim change runs `endUpFallback`, which clears the request. Rung 3 (0.7 s) is the last rung, so it is not allowed to force, and it logs `landed=1` on the wrong card. That is the BUG-156 trailer-card case the fix was for. To answer the question asked: the comparison does not read a stale pre-push id. `report` and `noteFocusedItem` are two `onChange`s on the same binding, so they fire in one update, and the `@State` read inside the rung closure sees the new `focusedRowKey`. Whenever `focusedRowKey == origin` is true, `itemByRow` already holds the landed card. The gap is timing, not staleness. **Fix:** let the last rung force the remembered card too when the row already owns focus and the card is in the row (with item 2's membership check). `forceFirst` is only the right fallback for a row that does not own focus. Another option is a fourth rung at about 0.9 s, inside the 1.0 s expiry. Device pass: read which rung logs `force=1` on a walk where the origin was the playing trailer card.

4. **P2 (new in the fix): in the `.lift` state the tile's overlay title stays put while the tile grows 20 pt down over it.** `Screens/InlineTrailerCard.swift:2364-2385`. `CardArtworkFocusLift(mode: .manualScale…)` now scales `trailerSurface` about its own centre by `1 + 2·20/h`, so its bottom edge drops 20 pt. The VStack gap below it is `Theme.Spacing.md` (16 pt), and the `showsOverlayTitle` text below carries no `CardCaptionFocusDrop`, so the lifted surface and its 22 pt / y+10 shadow overlap the title by about 4 pt. That is BUG-36's "caption hidden under the lifted artwork", now in portrait rows with Show Titles on, Zoom on and the ring off: Steven's configuration. At the reveal edge the text also jumps up by about 20 pt as the base card's caption fades out, because that caption is dropped by `CardCaptionFocusDrop` while the tile title is not. Before the fix, the system lift scaled the whole label, title included. **Fix:** give the overlay title `.modifier(CardCaptionFocusDrop(mode: .manualScale, isFocused: isFocused && liftStyle == .lift, artworkHeight: artworkHeight))`, the same modifier the base caption wears, so both cards move their title the same 20 pt. On the device, also watch the reveal hand-off. `.focusEffectDisabled` switching on mid-focus deflates the system lift on the label while the tile's 0.15 s manual scale inflates, which can read as a dip. If it does, delay the flip of `tileShowingItemId` until the tile is fully opaque.

5. **P2 (round-1 P2-4, partly fixed): swipes never retire the pop restore.** `HomeView.swift:1804-1811`. The cancel runs only for `source == "press"`, and `.onMoveCommand` is fed by directional button presses only (the file's own rc13 note at `:1655`). A touch-surface swipe, Steven's normal input, goes through the focus engine. The window-level catcher only calls `handleRowsMove(.up, source: "swipe")` for an Up swipe that moved no focus, and the cancel excludes that source as well. Failing scenario: Back from a folder, then swipe Down to the next row (or Up into the hero) within 0.7 s while rung 1 or 2 has not landed. The claim change clears the request, but the rungs still run on the same generation, so rung 2 or 3 sees `focusedRowKey != origin` and sends a new request. The origin row's focus is nil, so it passes the anti-theft guard and pulls focus back: the stale-request class round 1 named. A swipe inside the row before 0.3 s can also be undone by a forced rung (item 3's timing makes that rare). **Fix:** retire on focus movement, not only on the press. In `handleRowFocusOwnership(owns: true)`, when `returnPending` and the claiming row is not the origin, bump `returnGeneration` and clear `returnPending`. Do the same on a hero focus gain while `returnPending` (`.onChange(of: heroFocused)`). Keep the press cancel for the in-row case. Accept `source == "swipe"` in the cancel too. The hardware evidence (09-30, 28/28) shows consumed Up presses reaching `onMoveCommand`; that consumed Down, Left and Right do the same is assumed, not shown. Add that to the device pass.

6. **P3: the round-1 P2-4 Stage half was not done and not declined.** `Screens/Home/StageController.swift:177-201` and `StripPager.runRung`. The Stage uncover restore runs the pager rungs out to 1.0 s. The pager drops a stale request when another strip row claims focus (`dropStaleRequest(keeping:)` at `StripPager.swift:390`), but nothing cancels it when Up from row 0 reaches the tab bar or the rail during the rungs. A later rung, whose row focus is nil, then pulls focus back into the strip. The commit message lists the declined round-1 items, and this one is not among them. Either cancel it on `stripFocusLost()` while an `uncover` restore is pending, or record the decline in the batch record.

7. **P3: the zero-publish coalescing is one runloop turn, which may be shorter than the folder → Detail gap, and the probe still logs the dropped pop.** `DesignSystem/TabBarVisibility.swift:54-74`. A folder's `onDisappear` and Detail's `onAppear` in a NavigationStack push usually fire at opposite ends of the transition (appear at the start, disappear at the end), which gives the safe order 1 → 2 → 1. When they invert, they need not land in the same or the next runloop turn, and `DispatchQueue.main.async` covers only the next. Separately, `TabBarStateProbe.notePop()` and `TabBarProbe.recordPop(depthAfter: 0)` run on the synchronous 1 → 0 even when the publish is later dropped. That is a phantom `r=pop` in the BUG-66 probe, which the method's own doc calls worse than none. **Fix:** move `notePop()` into the deferred block, after the `pendingZeroPublish` check. If device logs still show a blip, defer by a short `asyncAfter` (about 50 ms) instead of `async`. The rest of item (e) is clean: the flag is set before the write, `didSet` publishes rises immediately and drops a pending zero, and a double 1 → 0 queues two blocks whose second no-ops. Every reader of `homeSurfaceCovered` that runs at the pop (`syncHeroFocusCover`, `StageStripHome.syncCover`, the swipe guards) already saw `true` until Detail's `onDisappear` at the end of the transition before this change, so one more turn changes nothing they depend on; the `onReceive` subscribers get the publish when it happens.

8. **P3: the landscape-row memo and Home's floor decision can disagree.** `DesignSystem/PosterStyle.swift:95-106` against `Screens/HomeView.swift:2895`. `CatalogRowView` reads the memoised answer keyed on (count, first id, last id), and Home's short-row floor (`isLandscapeShapeCatalogRow`) calls the uncached `landscapeSection(items:)`. A reload that keeps the ends and count but changes items in between (enrichment refreshing `posterShape`, a catalog that rotates its middle) gives a stale memo while Home re-decides. The floor and its cancelling `shortRowCompensation` then disagree, which is BUG-122's geometry mismatch. It is rare, and isolation is fine: the target builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so `resolved(forSectionItems:)` and its only caller (`BrowseComponents.swift:5101`) are main-actor. **Fix:** have Home call the cached function too, so the two can never disagree, or key on a cheap hash of all ids if a stale memo turns out to matter.

9. **P3: the cached-logo check covers only a head hit. A placeholder hit still flashes the loading text.** `DesignSystem/CachedAsyncImage.swift:170-178` against `ImageLoader.load` (`:1344-1375`). The body checks `ArtworkStore.cached(candidateURLs.first, decode: chain.request)`, the same normalised request the loader uses (`load` passes `chain.request`, and `cached` normalises again), so the head case matches exactly. But `load` also shows `cachedPlaceholder(for:)` (any bucket) or the last cached candidate when the head misses. For a logo decoded earlier at another size, or one served from its fallback, the title text still shows for one frame before the placeholder bitmap. Per-body cost is negligible: the loading branch only, one family lookup. **Fix (optional):** mirror the loader's order (`cached(head) ?? cachedPlaceholder(for: candidates)`). Also note that when the loader's fetch for this chain is still in flight and the head has since landed in memory, the slot shows `Color.clear` until the task completes, not the text. That is fine, but it is not a single frame in that case.

10. **P3: the landscape UI leg's skip condition can never be met on the 26.5 fixture.** `NuvioTVUITests/BatchAFolderUITests.swift:313-317`. `app.descendants(matching: .any).matching(hasFocus == true).firstMatch.exists` is true whenever anything is focused, which on tvOS is always, so `keyboardUp` is always true and the leg goes straight on to `typeText` and fails exactly as before. (On a 27.x runtime `hasFocus` never reports, so the guard comes down to `app.keys.count > 0 || field.hasFocus`.) **Fix:** drop the third term and test for the keyboard itself (`app.keyboards.count > 0` or `app.keys.count > 0`).

11. **P3: `walkToTopUntilBar` is safe but weak on Classic.** `BatchAFolderUITests.swift:89-98`. It never presses Menu, and Up on the tab bar is a no-op, so the walk cannot leave Home. The Up fallback can run during the walk, which is harmless. On Classic, Up from row 1 reveals the hero and the next Up reaches the bar, well within 8 presses. One caveat: a pass now proves that the bar shows once Home is at the top. It no longer proves the bar returned at the pop itself, so a regression that leaves `immersiveHidden` true for a few seconds after the pop would still pass. Assert `probe(...)` / the Developer `depth=0` readout right after the pop as well, if the harness exposes it.

## Answers to the specific questions

- **(a)** `.animation(value: isFocused)` inside `manualLift` sees the passed value `isFocused && liftStyle == .lift`, so the reveal edge (where `liftStyle` flips) animates the scale in over 0.15 s, and the black `.background` fades in with it, because it is inserted inside the animated transaction. The background is attached to `trailerSurface`, so it always takes the surface's current layout frame: during the poster → 16:9 width morph, the rect follows whatever the model's stage transaction animates, with no separate tracking. The `.lift` state does not need a separate card-focus input. `@Environment(\.isFocused)` in `InlineTrailerCard` is the button's focus, and the AND turns the lift off the moment focus leaves, before the stage collapse. `.hoverEffect(_:isEnabled:)` is tvOS 17+, and the deployment target is 26.0. Remaining issues: item 4, and the round-1 device check that `.focusEffectDisabled(true)` really removes the `.borderless` platter.
- **(b)** `.zIndex` on the per-item wrapper changes neither layout nor identity (it sits outside `.id(item.id)`'s target and changes no frame), so the BUG-29 morph-scroll math (frame-based) and the BUG-92 leading-edge clip allowance (already sized for a 16:9 tile × lift scale) are unaffected. It is needed: the manual scale overhangs a 16:9 tile by about 35 pt a side. It is applied in landscape rows too, where it is inert.
- **(c)** `target` returns the request's `itemId` without checking that the row contains it. A stale id is written as-is. Before the fix that only happened into a focus-less row, which was harmless. With `forceCard` it can now replace a focused card (item 2).
- **(d)** `handleRowsMove` is reached for every direction (`.onMoveCommand` on the rows ScrollView, `:1654`), and consumed Up presses are proven on hardware. The cancel clears `rowFocusRequest` only when `activeUpFallbackTarget == nil`, so an Up fallback that owns the request is left alone, and the Up press that cancelled goes on to start its own attempt. Gaps: swipes (item 5) and the never-cleared forced request (item 1). The forced comparison: see item 3, the read is consistent and the timing is the problem.
- **(e)–(h)** See items 7, 8, 9, 10 and 11.

## Verified fixed

- **r1 P2-1 (tile lift / landscape rows): fixed.** `.lift` is now portrait-only (`BrowseComponents.swift:5248-5249`). A landscape row keeps the system lift on the whole label, so base card and tile rise as one object and no base edge shows around the tile. In portrait the tile draws the lift itself, and the faded base card's hover effect is off. One new defect on this path: item 4 (overlay title).
- **r1 P2-2 (structural switch): fixed.** `CardArtworkFocusLift.systemLift` is one modifier chain, with `.hoverEffect(.highlight, isEnabled: liftStyle == .highlight)`. `content` sits in one structural position, so the artwork, its `CachedAsyncImage` loader and its overlays keep their identity at both tile edges.
- **r1 P2-3 (forced-card rung): partly fixed.** The mechanism is right and the read is consistent, but it only fires when the engine restores before 0.3 s (item 3). It also adds two new risks: the request is never cleared (item 1) and a stale id can be forced (item 2).
- **r1 P2-4 (press cancel): partly fixed.** Button presses in any direction retire the restore and leave an Up fallback's request alone. Swipes and focus movement do not retire it (item 5), and the Stage half is missing (item 6).
