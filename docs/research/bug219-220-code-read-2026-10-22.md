# BUG-219 and BUG-220: code read (2026-10-22, read-only agent on `fccfabb3b`)

Both were filed as P4 "to confirm" during the Wave 3 device pass. No code changed; both are Wave 4 candidates with the smallest fix named.

## BUG-220 — resume position lost after a relaunch when Watch Progress Source = Trakt

**What the device showed (Test 2, Trakt as the source):** an mpv session on a 106-minute film stopped at ~150 s; the Detail page showed Start Over right after the exit; after a kill and relaunch neither Continue Watching nor the Detail page carried the position.

**Writes are the same on both players.** mpv saves every 5 s (`MPVPlayerView.swift:2298-2304`) and flushes on `viewDidDisappear` (`:851-867`), then stops the Trakt scrobble; the native path does the same (`NativePlaybackCoordinator.swift:521-536`, `:1296`) through `PlaybackProgressRecorder.swift:93-111`, `:147-159`. Every write passes `syncRemote: false`, so the tvOS player never pushes to Nuvio Sync. `WatchProgressRepository.upsert` (`WatchProgressRepository.kt:1394-1508`) writes the local entry, puts an optimistic copy into the Trakt provider (`:1491`) and persists (`:1638-1649`) whatever the source is. Trakt gets exactly one call per session: `/scrobble/stop` (`TraktScrobbleRepository.kt:231-347`), fire-and-forget, no retry on a 4xx.

**What the Trakt setting changes (`watch_progress_source`, `TrackingSourceSettingsSyncService.kt:47`; default TRAKT, `TrackingSources.kt:33`).** Writes do not change. Reads do: `currentEntries()` (`WatchProgressRepository.kt:1749-1764`) runs through `projectWatchProgressSourceEntries` (`WatchProgressSourceProjection.kt:21-24`), which with a provider active keeps only local rows the provider cannot represent (`kitsu:`, `mal:`); any `tt…` / `tmdb:` / `trakt:` id counts as representable (`TraktIdUtils.kt:65-73`), so the persisted local row is loaded at launch (`:426-454`) and hidden. The Start Over seen right after the exit was Trakt's optimistic overlay: in memory only, three minutes (`TraktProgressRepository.kt:59`, `:541-555`), cleared on relaunch (`TraktTrackingProgressProvider.kt:98`). After a relaunch the position can only come back from `/sync/playback` (`TraktProgressRepository.kt:691-727`), held in memory.

**Thresholds:** none in our code drops 2.4 % of a film. Local keeps ≥ 1 s and completes at 90 % (`WatchingPolicies.kt:9-10`, `:26-34`); the Trakt mapping drops only ≤ 0 % (`TraktProgressRepository.kt:1314-1315`); Continue Watching and Detail have no minimum (`WatchProgressRules.kt:137-147`, `ContinueWatchingRow.kt:25-35`, `DetailCinematicLayout.swift:253-263`). Trakt saves a stop between 1 % and 79 % as a pause and returns 422 below 1 %. Side risk found on the way: `normalizeTraktProgressPercent` (`:1486-1494`) multiplies any value ≤ 1 by 100, so a Trakt row at exactly 1.0 % reads back as completed.

**Most likely cause:** with Trakt selected the only thing that survives a relaunch is the single `/scrobble/stop`, and several paths drop it silently (`buildItem` nil when no id parses, `:186-197`; no auth or a profile change, `:237-239`; a non-2xx other than 409, `:314-329`; the app killed before the request lands). The persisted local copy is never read back. Check first: the console's "Trakt scrobble stop response status=" lines (`:292-312`, debug level, may be absent in Release).

**Smallest fix:** widen the local-only merge rule in `WatchProgressSourceProjection.kt:23-32` so a representable local row that is in progress, not completed, and has no provider row with its `resolvedProgressKey` is kept, bounded to rows newer than the provider's last confirmed load so a removal made elsewhere is not resurrected. Cheaper and partial: retry the scrobble stop on failure.

## BUG-219 — Back from a pushed Settings page lands at the top of the pane

**What the device showed:** Subtitles & Audio › a pushed list page (`SettingsListPickerPage`) › Menu returns to the pane with focus on the first focusable row (the Text Color swatches), not on the row that pushed the page. The simulator came back to the right row (`docs/research/wave3b-sim-2026-10-21/wb-4c-after-page-pop.txt`).

**Why:** `SettingsListPickerRow` (`SettingsRowViews.swift:614-653`) is a value-less `NavigationLink { SettingsListPickerPage(...) }` (`:639-647`), not in `path` (`SettingsView.swift:57-58`); call sites `SubtitlesAudioSettingsPane.swift:42/49/56/70`, `SourcesSettingsPane.swift:183`. The page's `@FocusState` governs its own rows only and pops with `dismiss()` (`:713`) or Menu. The pane `List` (`SettingsPaneScaffold.swift:53-58`) has no `@FocusState` and no `defaultFocus` ("push lands on first focusable row", `:11`), so the return relies on tvOS focus memory alone, which `SettingsRootView.swift:17-20` already records as unreliable (the root backs it with `@FocusState` + `.defaultFocus`, `:173`, and a one-shot landing correction on pop, `:110-127`). `SettingsLinkRow` (`:844-882`) has no return mechanism either. Nothing re-identifies on pop (no `.id` on the scaffold List; `ContentView.swift:209` keys on theme / navigation / rail / font / discover).

**Smallest fix (the `ClaimsFocusAfterSwap` rule, `FocusRow.swift:29-42`, applied to the row):** `@FocusState rowFocused` on the `NavigationLink` plus a `@State reclaim` flag; the page takes an `onClose` closure called from its `.onDisappear`; the row's `.onChange(of: reclaim)` clears the flag and sets `rowFocused = true` one runloop late. `onChange`, not `onAppear`, because List cells may not re-fire `onAppear` on a pop. The same change on `SettingsLinkRow` covers every other pushed page.
