## Findings

1. **P2: BUG-158 `.lift` state takes the lift off the playing tile, and in landscape rows the base card scales out from under it.** `DesignSystem/PosterCard.swift:252` (`.focusEffectDisabled(liftStyle == .lift)`) and `:833-855` (`CardArtworkFocusLift`, `.lift` → `manualLift`). Before this change the system `.borderless` lift raised the whole label, base card and tile together, as `InlineTrailerCard.expandedTile` documents ("No focus scale of its own… moves the whole button label… as one object", `Screens/InlineTrailerCard.swift` ~2382). With the system effect off, the only manual lift is `CardArtworkFocusLift` on the base card's artwork. In portrait rows that card is at opacity 0 (`fadesBaseCard`), so the visible tile sits flat and the focused card drops about 20 pt at the reveal edge. In landscape rows (global toggle, or the new BUG-157 per-row landscape) `fadesBaseCard` is false, so the base `LandscapeCard` scales and casts its black shadow behind an unscaled tile of the same size, and its edges show around the tile. That is the doubled outline BUG-158 set out to remove. **Fix:** do not route `.lift` into the base card. Apply the manual scale and shadow once, to `expandingCard`'s ZStack (the whole label) when `cardSystemLiftStyle == .lift`, and leave the base card's `CardArtworkFocusLift` without a hover effect in that state. Confirm on the device that `.focusEffectDisabled` really suppresses the `.borderless` platter on tvOS 26/27. If it does not, BUG-158 is not fixed at all.

2. **P2: `CardArtworkFocusLift` branches on `liftStyle`, so the poster artwork is torn down and rebuilt at both tile edges.** `DesignSystem/PosterCard.swift:839-855`. `switch liftStyle { case .highlight: content… case .lift: manualLift(content) }` puts `content` at two structural positions. Each flip re-creates the artwork subtree, including `CachedAsyncImage`'s `@StateObject` loader (image back to nil until `onAppear` reloads), the watch badge and the ring overlays. The flip happens on reveal (hidden under the tile) and again on collapse, while the base card dissolves back in. That risks a shimmer or empty frame on every trailer collapse, the BUG-133 "empty dark frame" class. **Fix:** keep one modifier chain and drive it by value: `.hoverEffect(.highlight, isEnabled: liftStyle == .highlight)` (tvOS 17+), plus the background and `scaleEffect` gated on `isFocused && liftStyle == .lift`, so identity never changes. The same applies to item 1's new home for the lift.

3. **P2: the Classic pop restore counts as landed when focus is in the right row on the wrong card, so the cause BUG-156 names is not fixed.** `Screens/HomeView.swift:2366-2370` (`if focusedRowKey == origin.rowKey { … landed=1 … return }`) together with the anti-theft guard in `PinnedRowUpFallback.swift` `applyIfMatching` (`focus.wrappedValue == nil`). The commit's own diagnosis is that the engine loses the card when the focused view was replaced while covered (the morphed In Row trailer card) and falls back to a default candidate. If that fallback lands in the same row (its first card, for example), rung 1 logs `landed=1` and stands down, and the anti-theft guard would block a card-level correction anyway. Stage has the same shape: the pager's guard keeps "a row the engine already restored on its card", whichever card that is. **Fix:** compare the card too. `upInput.returnFocus.itemByRow[origin.rowKey]` is updated by `noteFocusedItem` as soon as the row reports. On rung 1 only (t≈0, before any user press can arrive), when the row owns focus on a card other than `origin.itemId`, issue a forced-card request that bypasses the anti-theft guard (for example a `force` flag on `PinnedRowFocusRequest`). Leave rungs 2 and 3 row-level. Whatever is chosen, the device pass needs a walk where the origin was the playing trailer card.

4. **P2: a restore rung can pull focus off a row the user has already moved to.** `Screens/HomeView.swift:2363-2376` (rungs at 0 / 0.3 / 0.7 s) and `Screens/Home/StageController.swift:183-201`. A rung stands down only when the origin row already owns focus. If rung 1 does not take (the row is not yet focusable mid-pop, or the engine's restore lands after the request), and the user presses Up into the hero or Down to another row before 0.7 s, rung 2 or 3 issues a fresh `PinnedRowFocusRequest` for the origin row. That row's own focus is nil, so the guard passes and focus is yanked back. This is the stale-request class BUG-112 F1/F5 closed. **Fix:** retire the attempt on the first user input after the pop. Classic already stamps presses (`HomeUpPressConsumption`, `lastRowFocusChangeAt`): bump `returnGeneration` on any directional press or select seen after the pop edge, or on a row claim by a row other than the origin once rung 1 has run. Give `restoreAfterUncover` the same cancel for Stage.

5. **P3: folder pages now cross immersive depth 1 → 0 → 1 on folder → Detail.** `Screens/CollectionsUI.swift:1381-1388`. The comment accepts this ("may touch 0 for that one transaction"), but `TabBarVisibility.recompute` publishes `immersiveHidden` on every 0↔>0 crossing. If the folder's `onDisappear` and Detail's `onAppear` land in separate updates, the system bar gets a hidden → shown → hidden pair, which is the BUG-66 mid-slide latch class, now on a common path (every Detail opened from a collection) where before it needed Detail → More Like This. In Rail mode the same blip moves the Hide While Browsing rail. **Fix (cheap):** coalesce the down-edge in `popImmersive`: when depth reaches 0, defer `recompute()` one runloop and skip it if a push arrived in the meantime. Watch for it in the device pass: folder grid → Detail in Tabs mode, then Back.

6. **P3: a folder pushed in Rail mode stays counted when the user leaves through the rail.** `CollectionsUI.swift:1381`. As the `TabBarVisibility` doc says, a tab switch does not fire `onDisappear` on Home's stack. With Always Visible, a user can open a folder, open the rail and switch to Library while `detailDepth` stays at 1. Hide While Browsing then treats every tab as immersive and keeps the rail hidden until they come back to Home. Detail already had this. Folders make it far more reachable, because a folder is a browsing surface where people open the rail. **Fix:** leave as is and note it, or make `RailVisibilityRule`'s immersive term follow the Home tab only (`homeTabSelected && depth > 0`).

7. **P3: Detail now shows the title text for a frame before a cached logo.** `DesignSystem/CachedAsyncImage.swift:170-171` + `DetailView.swift:1755`, `DetailCinematicHero.swift:208`. `loader.image` starts nil and loads in `.onAppear`, so even a memory-cache hit renders the loading branch first. With the shimmer that frame was a faint block. With the `hero`-sized title it can read as text → logo on every Detail open. **Fix:** seed the loader synchronously from the memory cache in `init` (`ArtworkStore.cached(...)`, as `InlineTrailerTitleOverlay` does), or show `loadingContent` only after about 120 ms. The two new inits are not ambiguous with the old ones (the `loading:` label is required), and the `AnyView` is built only in the loading state, so it costs nothing.

8. **P3: Open Last Profile can skip a PIN added on another device.** `Screens/ProfilesViewModel.swift:84-95`. The decision reads `pinEnabled` from the cached payload, before `pullProfiles`. A PIN set on the phone since this TV's last pull auto-enters without the PIN prompt. This matches upstream's rule, but the fork already treats stale PIN state as worth a pull (`verifyPin()` pulls first, upstream `5327166f`). **Fix:** after `select`, when the first pull reports the profile as `pinEnabled`, set `entered = false` (back to the picker, which asks for the PIN). Or accept it and say so in the setting's explainer.

9. **P3: one-frame picker before auto-enter.** `ContentView.swift:218-219`. `entered = true` is written in `.onChange(of: auth.gate)`, after the update that rendered `.main` with `entered == false`, so `ProfileSelectionView` can paint once (and its `onAppear` runs). **Fix:** gate the `.main` branch on a `pendingAutoEnter` flag computed synchronously, or show the loading view while the decision is pending. Cosmetic. The latch semantics are correct: one fire per process, `.welcome` consumes it, Switch Profile never comes back here, `profiles.start()` is idempotent, and the DEBUG override is never persisted.

10. **P3: the Search results page can be blank or stale while the field holds text.** `Screens/SearchView.swift:203-207`, `SearchViewModel.swift:455/469`. (a) Between the first letter and the debounce (350 ms), `queryIsEmpty == false` but `displayQuery == ""`, so the results page renders against an empty query. Check it shows the hold or loading state, not an empty-state flash. (b) `stop()` cancels the debounce. Type and switch tabs within 350 ms, and on return the field shows "abc" while `displayQuery` is "" or the previous query, and nothing re-fires because `.onChange` will not run again. That was latent before. Now it is visible, because the page used to echo the live text. **Fix:** in `start()`, if `activeQuery` differs from the box's trimmed text, call `queryChanged(box.text)` (the owner can pass the text in). Separately, the open-result path records Recent from the live text (`historyOnOpen.queryChanged(to:)`) while the quoted chip records `displayQuery`. Pick one.

11. **P3: `CatalogRowView.posterStyle` recomputes the majority scan on every read.** `Screens/BrowseComponents.swift:5100-5102`. The getter walks `section.items` (up to 100 Kotlin `posterShape` getters) on every access, and the body reads it about 8 times. The row body re-runs on every card hop (`focusedItemId`) and now on every tile edge, so that is roughly 800 bridge calls per hop on the BUG-126 hot path. **Fix:** compute `landscapeSection` once per section identity (in `init`, or a `let` derived from `section`) and keep the getter a cheap merge.

That is new per-focus work for every No Zoom user (cached per URL, so cheap after the first visit). `FolderTile` / `CastCard` still draw white `stillHighlight` rings, so a folder row next to a poster row now shows two ring colours in still mode. **Fix:** route FolderTile and CastCard through the same table, or note the gap in the batch record.

## Clean

Verified and found correct:

- **`CatalogInflightRequests` (Kotlin).** Every waiter count changes under one mutex, both `finally` blocks run under `NonCancellable`, and only a waiter that leaves while the result is still pending can cancel. A completed or failed fetch is never counted as cancelled. A joiner either keeps the old entry (it joined first) or starts a fresh one (it joined after `removeIfCurrent`). The cancelled job's `CancellationException` completes a deferred nobody awaits. `job` is assigned under the lock before any waiter can read it. There is no lock re-entry (the fetch's `finally` runs in its own coroutine), and the atomicfu counters are private class / top-level vals. Search really cancels its waiters: `SearchRepository.search` cancels `activeJob`, whose children are the catalog fetch waiters, so the fix reaches the network. Home or Discover waiting on the same key keep the fetch alive. The legacy switch is DEBUG-only.
- **`queryIsEmpty` / `displayQuery`.** The edge-only publish is correct. A chip tap writes the box and goes through `queryChanged`. Clearing the field resets `displayQuery`. The hold and requestId machinery is untouched. `SearchContent` holds only reference or nil inputs, so its body is skipped on keystrokes. `SearchPerfProbe` is entirely `#if DEBUG`.
- **Rail Hidden.** Precedence is right: focus and reveal show it, root cover hides it, and `.hidden` returns false before the immersive / Search / scroll terms. `reservedLeadingInset` gives 0. The B4 keyboard term cannot apply. The `updateRestingVisibility` early return leaves `restingShown` neutral (true), which `shown` ignores for Hidden. The failed-Left arm (`handleMoveFailed`) and the Menu reveal (`RailMenuRevealModifier`) do not depend on visibility. A mode change rebuilds the shell (`.id` key), so no stale `slideAnimation` survives.
- **Profile auto-enter latch.** See item 9. `rememberedStartupProfile` copies upstream's rule.
- **xcstrings.** JSON parses. All five new keys carry de/es/fr/it/vi, the same coverage as the other 1364 keys. The only key dropped is the old rail explainer the new one replaces. No existing entry changed.
- **Immersive push/pop balance.** One pair on `FolderDetailView` covers both layouts, a Rows ↔ Grid swap does not re-push, and `popImmersive` clamps at 0. `homeSurfaceCovered` is now true under a folder, which also stops the hero trailer's audio there, an improvement. `FolderRowsPage` drives its own `setCovered`, so it is not affected.
- **Classic return memory.** It writes to the box only (the BUG-126 rule holds; the DEBUG label is a leaf). The push edge falls back to the release grace. A push from the hero records no origin. `takeOrigin` is one-shot. A stale request is cleared by any claim change (`endUpFallback`) or by the 1 s expiry. The expiry's conditional clear cannot wipe a newer Up-fallback request for a different row. `PinnedRowSettle.setCovered(false)` runs before the restore.
- **BUG-157.** The majority rule, the env override handed down from the row (cards, `SeeAllCard`, the pinned title's style key), strip memory widths (`applyStripMemoryScroll` reads the resolved style), and the Classic short-row floor with its matching negative padding all line up with the BUG-122 mechanism. `pinnedLastRowHeight` stays consistent because the last row is floored anyway.
- **BUG-149.** `InlineTrailerTitleOverlay` observing `TitleLogoStore`: only the one playing tile mounts it, the store publishes per lookup batch rather than per frame, `url` stays cheap, and the lookup is kicked at most once per key.
- **BUG-159 / BUG-146.** `HeroFolderBoxLayout.split` keeps the box height fixed. `StripShelfPadding` keys on `stripFocusMemory` like `StripHeadingLineLimit`, so Classic's reach budget is byte-identical.
- **`InlineTrailerTileShowingKey`.** The preference → `@State` → environment loop has no feedback path: the environment never changes `tileVisible`.
