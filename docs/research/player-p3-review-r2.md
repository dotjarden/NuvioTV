## Checked and found clean

The controller closes an idle thumbnailer and sums the charge across reopens (`thumbBytesClosed` + live).
- **r1 #2 (P2), fixed.** The priming seek is capped at 16 MB through the interrupt gate, and `indexUsable` adds the 80 % span rule on top of the count. The Cue-less test needs the span rule: its 42 entries would pass the count check (600/30+1 = 21) alone.
- **r1 #3 (P2), fixed.** `firstSampleStartsTheMdat` gates both cuts, and the two new cases cover a wrong offset and an absent one.
- **r1 #4 (P2), fixed.** The version is bumped inside the actor on every `snapshot()`, so it is unique and increasing. Only `.empty` has 0. `applyStoreSnapshot` drops anything not newer. `insert` takes its snapshot synchronously at return, so a higher version always means later state.
- **r1 #5–#11, fixed as described.** #5 operand order. #6 `viewDidDisappear` cancels, stops and closes, and `destroyPlayer`'s `thumbnailer?.close()` on nil is a no-op. #7 `m3u8/m3u/mpd` by path extension; `pathExtension` ignores the query. #8 the description says "about 200 MB". #9 `%ld` in the key. #10 the env var is read as `THUMB_FIXTURE_URL` (xcodebuild strips the `TEST_RUNNER_` prefix) and skips are loud. #11 the leg window is 3 s with a SLOW line.
- **r1 #12** was a device-pass note. It stands.
- **FFmpeg range behaviour.** `initial_requests` is set in `http_open` (`seekable != 0 && initial_request_size > 0`) and cleared only on a range end (`EAGAIN`, "continue streaming uninterrupted") or when the stream is not seekable. `http_seek_internal` never re-arms it. So after an open that never reached a range end, every later request, seeks included, uses `initial_request_size`, and setting both keys is the right fix. `av_opt_set(pb, …, AV_OPT_SEARCH_CHILDREN)` reaches `HTTPContext`: the avformat-owned `AVIOContext` (`ffio_fdopen`, no custom AVIO here) has `ff_avio_class`, whose child is the `URLContext`, whose child is the protocol's private context. That holds for `https`, which uses the same option table. Both reads happen per request in `http_connect`, so the next seek picks up the new size. With `multiple_requests` 0 the server answers `Connection: close`, `willclose` is set and the soft-seek drain path is never taken. This runs inside `doOpen`, on the thumbnailer queue.
- **Byte gate.** The reader closure captures the `AVFormatContext` pointer. It is armed and disarmed around the one `av_seek_frame` on the queue, and the interrupt callback runs on that thread, so the pointer is live whenever the reader runs. The opaque pointer is still the stored `let gate`. `retry_transfer_wrapper` checks the interrupt before each protocol read, so the overshoot is one read (the test allows cap + 2 MB). The `error`/`eof_reached` reset runs only when the byte stop fired. In that case the last read was interrupted, not at EOF, and `avio_seek` clears `eof_reached` on the next seek anyway. A stale `error` would only surface on a later zero-byte read, so the reset is benign and cannot hide a real EOF.
- **Idle close state machine.** Jobs start and the idle check runs in that order inside `driveThumbs` on main. `next` sets `inFlight` through `noteStarted` before the idle check reads it, so a decode can never be dispatched and then closed under. `transport.mode == .scrubbing` covers the whole scrub session, so no close happens mid-session. `openThumbnailer` guards `thumbnailer == nil`, and a close nils it synchronously, so two live thumbnailers can only overlap during the old one's async `close()` block, on separate serial queues with independent contexts. `thumbFacts` and `thumbBytesClosed` are per controller, and a controller has exactly one `loadfile` and a `let context`, so a next episode or an engine retry gets fresh values.
- **`viewDidDisappear`.** It only runs that block when `isLeavingPlayer`, and the post-play cover does not set that flag, so a controller that is shown again never reads `.modeOff`. `thumbStopWords(.modeOff)` is nil anyway.
- **I-frame check vs movenc.** In fragmented mode, `mov_write_trun_tag` writes `moof_size + 8 + track->data_offset + cluster[0].pos`, which is `moof + 8` for the remuxer's separate video segments (the native smoke serves video and audio as separate playlists).
- **DEBUG hygiene.** The new `NSLog`s (idle close, range resize refused, priming cap, open line) are all under `#if DEBUG`.

## P2

**1. After the pre-warm stops, every scrub session pays a full reopen, and the reopens use up the scrub ceiling** (`MPVPlayerView.swift:2044-2053`, `ThumbScheduler.swift:221-229`, `KeyframeThumbnailer.swift:131`, `:267`, `:451`).
The idle close fires 2 s after the last scrub job's decoder release, as soon as the transport leaves scrubbing. The pre-warm stops on every long title (budget, frame cap or store full), so from then on each scrub session reopens: connect, TLS, header, `find_stream_info`, then a first frame charged as three requests. Each reopen charges `5 × 512 KB` plus what it consumed, although a reopen skips priming, and `3 × range` for the first frame. That comes to about 3.5–4 MB at 1080p and 6–9 MB at 4K, against a 50 MB ceiling headroom. Failure scenario: on a 4K remux, a viewer who scrubs, plays, and scrubs again gets a first picture that waits for an open (the UI leg had to widen its window to 3 s for this reason). After roughly six to twelve sessions, `nextScrub` hits `scrubCeiling` and `stop(.byteBudget)` switches decode off for the rest of the file ("decode off: budget used"). Before this round, the thumbnailer stayed open across sessions. The connection problem r1 #1 named is mostly gone without the close: at ≤ 1080p a frame range now completes (`end=complete` in the fix agent's log), so the host has already closed the connection. Fix: keep the thumbnailer open while idle and close it either after a long idle (e.g. 60 s since `noteScrubEnded`) or only when the last request was left unfinished (4K, or an open range). Charge a reopen's open as the requests it actually makes (two or three without priming), not five.

## P3

**2. Budget floor.** `byteBudget` (`ThumbScheduler.swift:101`) is 2 % of the file, and one open is now charged about 3 MB, so any file under about 150 MB never decodes a pre-warm frame. It still pays the open and the idle close (the 116 MB fixture needs `-debug.thumbBudgetMB 20`). A 300 MB TV episode gets 6 MB, which is about 10 frames at 288 KB each. Recommendation: `max(min(size / 50, 150 MB), 16 MB)`, capped by `size / 10` so a tiny file cannot spend more than a tenth of itself. At minimum, skip the pre-warm open when the budget is below one open charge plus 8 frames.

**3. "MB read" now shows the charge** (`MPVPlayerView.swift:2002`). The number is an upper bound (at 1080p, 32 KB consumed is charged as 288 KB), so a tester comparing it against a proxy will see the Info row read 5–9 times high. Use "MB used", or show consumed and charged in the DEBUG suffix.

**4. No post-fix proof on a real remuxer segment** (`IFrameFragment.swift:118-121`). The new cases are synthetic. The real-segment trim CLI ran before this check existed. If movenc's offset differs on some input (an edit list, a non-zero `track->data_offset`), every I-frame 404s and native scan loses its pictures without an error. Rerun the native smoke with `-debug.remuxSmokeScanRate` (or the trim CLI on `seg-*.m4s`) and record `0 × 404` with the gate.

**5. The cap-1 test does not exercise what its name says** (`KeyframeThumbnailerTests.swift`, `testPrimingCapKeepsAnIndexThatSpansTheFile`). With a 1-byte cap, the first protocol read after the Cues seek still goes through, and the fixture's Cues fit in it. So the test proves "one read passes" and that a frame works after a byte stop. That second part is the error-reset path, but it would probably pass without the reset as well (`avio_read` surfaces `pb.error` only on a zero-byte read). Rename it, and assert `byteLimitHit` so the test fails if the cap never fired.

**6. Open charge count is fixed at five** (`KeyframeThumbnailer.swift:131`). An MP4 with `moov` at the end, or a `find_stream_info` that crosses several ranges, can make more than five requests. Each request that crosses a range end is fully consumed, so only the unread tails are missed, but that can still undercount by a few 512 KB tails. Counting requests instead would make the charge exact: compare the `[http]` request log against a counter wrapped around `io_open`, or read `AVIOContext.seek_count`.

**7. `%d` with `Int` again in a DEBUG log** (`KeyframeThumbnailer.swift:382`, `index=%d` with `index.count`). Same issue as r1 #9, debug only. Use `%ld`.
