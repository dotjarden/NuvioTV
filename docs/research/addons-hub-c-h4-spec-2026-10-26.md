## 0. Decision on "Follow add-ons order"
The shared repository has no such preference (`HomeCatalogSettingsRepository.kt`: `moveUp`/`moveDown`/`moveByIndex` only, order persisted per catalog and SYNCED through `HomeCatalogSettingsSyncService`), and a new synced preference needs mobile parity. H4 ships it as a one-shot action instead: **"Match add-ons order"** reorders the catalogs once to the installed add-ons' order; a persistent switch is recorded as an open decision for Christian. Record this in the view's doc comment.

- Title `Text("Catalogs")` (`screenTitle`, `addons_hub_catalogs_title`), explainer `Text("Switch each catalog on or off and set the order of your Home rows. Collections stay pinned where Home keeps them.")` (`body`, secondary).
- Action row (`.focusSection()`): **Match add-ons order** (`.buttonStyle(.chip)`, `arrow.up.arrow.down`, `addons_hub_catalogs_match`): `model.matchCatalogsToAddonOrder()`; a toast "Catalogs now follow your add-ons order." after it (the hub's toast pattern, `addons_hub_catalogs_toast`).
- One `CatalogRow` per `model.catalogs` item where `!item.isCollection`, `ForEach(..., id: \.key)`, index-based identifiers `addons_hub_catalog_<i>`: the same shape as `AddonCardView` — a container `HStack` on `Theme.Palette.surface`, `Theme.Radius.card`, padding `lg`, one `.focusSection()`; name area = `Button` (`.settingsRow`, action = toggle) with `item.displayTitle` (`sectionTitle`), `item.addonName` (`caption`, secondary), and a `Text("Disabled on Home")` in `Theme.Palette.error` when `!item.enabled`; then three `.chip` controls: On/Off `SettingsSwitchGlyph(isOn: item.enabled)` (`_toggle`, label "On"/"Off"), ↑ (`_up`, disabled at the first row), ↓ (`_down`, disabled at the last row). ## 2. `SettingsViewModel` additions
- `var addonOrder: [String]` published (names of `enabledAddons` in order, set wherever `enabledAddons` is set).
- `func matchCatalogsToAddonOrder()`: `let desired = Self.catalogOrderFollowingAddons(items: catalogs, addonOrder: addonOrder)`; then `for (from, to) in Self.movesToReach(current: catalogs.map(\.key), desired: desired) { HomeCatalogSettingsRepository.shared.moveByIndex(fromIndex: Int32(from), toIndex: Int32(to)) }` — NOTE `moveByIndex` indexes `allOrderedKeys()`, which includes collections; so compute `current` and `desired` over ALL `catalogs` keys (collections included, kept in place) and never move a collection. Then `refreshHome()` (private today; call it).
- Pure, `nonisolated static`: `catalogOrderFollowingAddons(items: [HomeCatalogSettingsItem], addonOrder: [String]) -> [String]`: collections keep their current positions; the other items are stably sorted by `addonOrder.firstIndex(of: item.addonName) ?? Int.max`, ties by current order. `movesToReach(current: [String], desired: [String]) -> [(from: Int, to: Int)]`: a selection pass that, for each index i, moves the item that should be at i from its current position to i (skipping when already there); returns [] when equal or when the key sets differ.
- Tests in `AddonsHubSummaryTests`: a fixture of five items (add-on names B, A, A, collection, B with `addonOrder` [A, B]) → the order A, A, B, B with the collection at its index; `movesToReach(["c","a","b"], ["a","b","c"])` → `[(1,0), (2,1)]`; equal lists → `[]`; different sets → `[]`.
