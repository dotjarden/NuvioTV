## The key question: does the pop's own Back press end the restore at once?

No. The feature is not a no-op. The order is:

1. The Menu press is stamped in `ViewerInputRecognizer.pressesBegan` (`Screens/Home/ViewerInputClock.swift:101-107`). Window gesture recognizers see a press before the responder chain, and `record` posts `didRecord` synchronously on main (`:56-60`). At that moment the biography is still on top and the Detail page underneath has `popRestoreRow == nil` (it is set only in `restoreDetailFocusIfArmed`), so the page's `.onReceive` (`Screens/DetailView.swift:1077-1079`) does nothing.
2. The pop runs, and Detail's `.onAppear` (`:1112-1121`) calls `restoreDetailFocusIfArmed`, which stamps `started` and calls `goLive(..., startedAt: started)` (`:2440-2444`). `started` is later than the Back press's stamp, so `hasInput(since: popStartedAt)` (`:851`) and the rungs' `hasInput(since: started)` (`:2448`) both read false for that press.
3. The press's END is never recorded (`pressesEnded` only counts down), and a thumb resting on the clickpad does not reach the 40 pt swipe travel.

The one case where the onReceive fires on a Back press with a restore live is a push and Back inside the 1.3 s window of an earlier pop on the same page. It then ends the earlier restore, which is right; the new pop's `goLive` resets the box's held change and counters.

A consequence worth knowing: the clock posts synchronously when the press begins, before the engine's move reaches SwiftUI, so for viewer input the `.onReceive` ends the restore BEFORE the `focusedRow` change arrives. The gate's `.release` branch (`:852-853`) is now effectively unreachable (by the time the change lands `popRestoreRow` is nil and the gate is skipped). Keep it as a backstop; no change needed.

## P3

1. **The held change keeps a stale `old` across a landing.** `Screens/DetailView.swift:854-855` (the `.landed` case) falls through to `handleFocusRowChange(old:new:)` but leaves `focusMemory.heldFocusChange` as it was, and `holdFocusChange` keeps the FIRST `old` of the run (`Screens/Detail/DetailFocusMemory.swift:91-93`). Sequence: held `A -> X`, then `X -> target` (landed, the handler runs with `old: X`), then an engine move `target -> Y` (held again). The box now holds `(A, Y)`, and the retire replays `handleFocusRowChange(old: A, new: Y)` although the handler last processed `target`. `old` feeds `heroReturn`, `heroExit` and `DetailRowAnchor.direction`'s `oldTop`, so the replay can choose the wrong direction or skip the hero return. The common hardware path (`cast -> nil` held, `nil -> cast` landed, the late engine restoration `cast -> nil` held) is unaffected, because there the first `old` is the target anyway. I checked the double-run case too: no single change can run the body twice. A replay needs `focusedRow == held.new`, and the only change that could bring focus back to `held.new` without updating the box is a `.release`, which is unreachable (see above).
   Fix: drop the held change whenever the handler runs during the live window. In `DetailFocusMemory` add `func dropHeldFocusChange() { heldFocusChange = nil }`. In the `.landed` case at `DetailView.swift:854`, call `focusMemory.dropHeldFocusChange()` before the stamp line. Add a unit test in `iosApp/NuvioTVTests/DetailFocusReturnTests.swift` for the box: `holdFocusChange(cast, nil)`, `holdFocusChange(nil, logos)` gives `(cast, logos)`; `dropHeldFocusChange()` then `holdFocusChange(cast, nil)` gives `(cast, nil)`; `endRestore()` returns it and a second `endRestore()` returns nil. None of the new box API is test-covered today (the only test touch is `endRestore()` at `DetailFocusReturnTests.swift:178`).

2. **`DetailPosterLinkRow`'s default outlives the restore and arrives one runloop late.** `Screens/DetailView.swift:3120` reads `restore`, which is `detailFocusRestore`. That value is set by the first rung (`asyncAfter(.now() + 0)`, one runloop after `onAppear`) and cleared only at the retire (`:2454`). Two consequences. (a) A viewer press ends the live restore through `.onReceive`, but this row keeps the remembered card as its `.userInitiated` default until 1.3 s. A viewer who leaves the row and comes back inside that window is pulled to the remembered card instead of the geometric neighbour. (b) The Cast/Studios defaults follow `popRestoreRow/Key`, which are set synchronously in `onAppear` and cleared in `endPopRestore`; these two rows follow a different clock. This is the input round 1 asked for and the fix pass did not use.
   Fix: give `DetailPosterLinkRow` a `livePopKey: String?` input. Pass `popRestoreRow == .collection ? popRestoreKey : nil` at the Collection call site and `popRestoreRow == .moreLikeThis ? popRestoreKey : nil` at the More Like This call site. Change the modifier to `.defaultFocus($focusedId, livePopKey ?? "", priority: .userInitiated)`. All four rows then share one lifetime that ends on viewer input. The `""` sentinel is fine on a normal open (no `MetaPreview` id is empty in practice; if one ever were, that card would become the row's default, so a `guard !item.id.isEmpty` in the feed is the belt if wanted).
