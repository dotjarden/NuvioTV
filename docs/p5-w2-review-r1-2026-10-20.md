## P2

### P2-1. The post-play row skips Detail's unreleased filter and custom-poster overlay

`shared/src/commonMain/kotlin/com/nuvio/app/features/details/MetaDetailsRepository.kt:308-312`

D4 says the row follows Detail's More Like This. Detail shows `uiState.meta.moreLikeThis`, and every write to `uiState` goes through `withUnreleasedFilter()` (`:97`, `:104`, `:136`, `:438`, `:468`). That call applies the DETAILS custom-poster pattern and, when "hide unreleased content" is on, drops unreleased titles (`:658-671`). `moreLikeThis` only matches that on one path: `peek` returns filtered meta, and the meta already carries a source. Two paths skip the filter:

- `fetch(type, id)` (cold cache: the Home resume cover, or Detail evicted) returns raw `baseMeta` or the TMDB standalone meta.
- Any meta without a source, including a peeked one, goes through `applyMoreLikeThisSource`. Its Trakt and Simkl branches replace the list with unfiltered items.

So a viewer with hide-unreleased on can get unreleased titles in the post-play row that Detail would never show, and custom posters differ from Detail's row.

Fix: filter both entry points. `withUnreleasedFilter` is private to the object, so it is in scope here:

```kotlin
suspend fun moreLikeThis(type: String, id: String): List<MetaPreview> =
    resolveMoreLikeThis(
        meta = peek(type, id) ?: fetch(type, id)?.withUnreleasedFilter(),
        apply = { meta ->
            applyMoreLikeThisSource(meta, fallbackItemId = id, fallbackItemType = type).withUnreleasedFilter()
        },
    )
```

The filter is idempotent: it keeps `rawPosterUrl` and drops only whole items, so running it twice on the peek-then-apply path is harmless. `resolveMoreLikeThis` and its tests stay as they are.

## P3

### P3-1. A pick can stay pending past a picker that does not close

`iosApp/NuvioTV/Screens/StreamPickerView.swift:512`, `:1480-1516`; presenters `DetailView.swift:1243,1265`, `EpisodesSection.swift:225`, `HomeView.swift:1313`

The presenter stores the pick the moment the poster is pressed. It is pushed on the picker cover's next `onDismiss`. That is right for the normal close (`afterPlayerClosed` → `.closePicker`). If the close outcome is `.raiseAlert`, `.openFailoverPicker` or `.keepList`, though, the picker stays open. This happens when a late failure is queued at the end, or a failover walk is still running. The pick then stays in `postPlayPending`, and the viewer's later plain Back from the list pushes a Detail page they chose minutes before. It is not an EJECT (the push still waits for the cover to go), but a route fires on a normal exit, which the rule forbids.

Fix: keep the pick in the picker and hand it to the presenter only on the closing branch.

```swift
@State private var postPlayPick: MetaPreview?
// PlayerScreen(... onOpenTitle: onOpenTitle == nil ? nil : { postPlayPick = $0 })
// handlePlayerDismissed(), right after `guard selected == nil else { return }`:
let pick = postPlayPick
postPlayPick = nil
// in `case .closePicker:` before `closePicker()`:
if let pick { onOpenTitle?(pick) }
```

The presenters' code is unchanged. `StreamPickerExitPolicy` is not touched.

### P3-2. The row's load competes with playback start (BUG-167)

`iosApp/NuvioTV/Screens/MPVPlayerView.swift:4794-4796`, `iosApp/NuvioTV/Screens/NativePlayerScreen.swift:251-253`

The loader starts in `onAppear`, which is the same moment the stream starts opening. On a warm Detail cache the call is free: `peek` hits `uiState`, and a resolved source returns at once. On a cold cache it is not. The Home resume cover is always cold for a title Detail has not shown. There `fetch` runs `resolveMetaLookupId` (up to 5 s) and `findReadyMetaManifests` (up to 10 s), then sequential 5 s addon fetches, then a Trakt or Simkl call. `fetch` never leaves the main dispatcher (unlike `load`, which parses on `Dispatchers.Default`), so the add-on JSON is decoded on main during the player's first seconds. That is the window Wave 3 is trying to shorten.

Fix: start the load once playback is running. mpv: move the call into `.onChange(of: state.playbackStarted) { _, started in if started, onOpenTitle != nil { moreLikeThisLoader.load(...) } }`. Native: add `if phase == .playing, onOpenTitle != nil { moreLikeThisLoader.load(...) }` to the existing `.onChange(of: coordinator.phase)` (`:231`). `loadedKey` already makes repeat calls no-ops.

### P3-3. The native tick reset can only fire spuriously while the cover is up

`iosApp/NuvioTV/Screens/NativePlaybackCoordinator.swift:1289`

While `didPlayToEnd` is true and Up Next is hidden, the cover is up and the viewer cannot seek. A Menu close calls `clearEnded()`. So `pos < dur - 2` only matters in two cases:

- The legitimate one: an AVKit scrub back while an Up Next card hides the cover.
- A spurious one: an item whose end position lands short of `item.duration`, from rounded `EXTINF` or audio running past video. The 3 s tick then flips the flag, and SwiftUI drops the cover by itself.

Fix: gate the reset on playback actually running:

```swift
if self.didPlayToEnd, pos < dur - 2, player.timeControlStatus == .playing { self.didPlayToEnd = false }
```

## Checked and fine

- **EJECT rule, all presenters.** DetailView (`showStreams` cover `:1235-1239` and the `seriesPlay` cover `:1249`), EpisodesSection (`:207-211`) and HomeView (`:1294-1298`) all set the route only inside the cover's `onDismiss`. On tvOS that fires at the end of the dismissal. The chain is: poster → `onOpenTitle` stores → `onExit` dismisses the player cover → `handlePlayerDismissed` → `.closePicker` → `closePicker()` → the presenter cover's `onDismiss` → push. Nothing pushes while a cover is up. The pending value is only set by a pick and is cleared on the first `onDismiss` that reads it (apart from P3-1).
- **DetailView's destination.** `.navigationDestination(item: $postPlayRoute)` sits at the root of the body chain, not inside a lazy container. `EpisodesSection`'s closure writes `postPlayRoute` directly from its own `onDismiss`, as the spec says. Every `DetailView` is inside a NavigationStack (Home, Library, Search, Discover, DeepLink `:83`), so the item destination always has a stack.
- **Paths that get no row.** The deep link resume (`ContentView.swift:306`), the local file (`LibraryView.swift:118`), the nested Up Next failover picker (`StreamPickerView.swift:521`) and the smoke rig with the knob off all pass a nil `onOpenTitle`. They show the old two-button screen.
- **Native end observer.** It is installed in `observePlayback`, so all three entry points get it: the first start (`:1111`), the pre-playback retry (`:1039`) and the B17 rebuild (`:787`). Each install removes the previous observer, so an item swap never leaves a stale one. The `playerItem === item` guard drops a late post from a replaced item. `stop()` removes it. `queue: .main` plus `assumeIsolated` is correct. Live and 0-duration items never post `DidPlayToEnd` (no ENDLIST). The tick's `dur > 0` guard keeps them out of the reset. Several posts while the flag is already true do not re-present anything.
- **Native gate and Up Next.** `didPlayToEnd && upNext.phase == .hidden` matches mpv's gate. With a countdown or Still Watching card the cover stays down. `.noStream` hides after its delay and the cover follows. The countdown hand-off sets `.hidden` and calls `onPlayNext` in one turn, the same as mpv, and the screen is replaced by `.id(ctx.id)`. `noteUserSeek` clears the flag on skip and chapter seeks, and a seek to the end raises it again.
- **`replayFromStart` and `clearEnded`.** Play Again dismisses the cover (the binding setter calls `clearEnded`), then seeks to zero with zero tolerance and plays. It routes through `noteUserSeek(to: 0)`, so a replay during a B17 rebuild is recorded. `handlePrePlaybackItemFailure` is untouched.
- **mpv.** The old `private struct PostPlayView` is gone with no other references. The only users are `MPVPlayerView.swift:4784` and `NativePlayerScreen.swift:222`. With `onOpenTitle == nil` or an empty list, the shared view renders the old screen (poster 260x390, title at 3 lines, the same two buttons and copy). Play Again stays first in reading order, so it keeps default focus. The row is a `.focusSection()` below the buttons. The cover's `onDismiss` keeps `reclaimFocus`.
- **DEBUG-only knobs.** `debug.postPlayStubTitles` and `stub(_:)` sit in `#if DEBUG`. `MPVSmokeModifier` (with `debug.mpvSmokeResumeSec`, `debug.mpvSmokePostPlay` and the `debug_postPlayOpened` label) is inside the file's `#if DEBUG`. `resumeAtSec > 10` beats `startFromBeginning` on both engines, so the legs' `-debug.mpvSmokeStartOver YES` does not cancel the resume.
- **Loader.** The class is `@MainActor` and its `Task` inherits main, so the K/N suspend call starts on main (needed for K/N's Swift suspend export) and `items` is written on main. `loadedKey` stops duplicate loads when `onAppear` fires again after a cover. A native-to-mpv fallback makes a new screen and loader; that second call is cheap after the first one has cached. Errors and `try?` give `[]`. The task is not cancelled when the screen goes, but a Swift cancel would not reach the Kotlin coroutine anyway, and `[weak self]` makes the late write a no-op. `contentType` and `parentMetaId` are the series type and id on every presenter path (`DetailView.swift:1254`, `EpisodesSection.swift:216`, Home's `parentMetaType` and `parentMetaId`). So series episodes look up the show, and the filter drops the show itself.
- **Shared Kotlin.** `moreLikeThis` never writes `_uiState` or `activeRequestKey`. `peek` only reads. `fetch` writes the cache through `putCache`, which checks the generation on main, so a concurrent `clear()` still wins. Detail's singleton state is untouched; the only overlap is a duplicate Trakt or Simkl call when Detail is enriching the same title at the same moment. The `@Throws(Throwable::class)` bridge turns Kotlin exceptions into Swift throws instead of a crash, and is exported the same way as `fetchChecked`.
- **Tests.** `MoreLikeThisResolutionTest` covers the four branches of `resolveMoreLikeThis` (no meta, a resolved source, the chain applied, the chain turning the source off). `PostPlayMoreLikeThisTests` covers the four filter rules from the spec. Not unit-tested: the native end-flag rules and the presenters' pending hand-off. Both are covered only by the UI legs and the device pass, which is acceptable for this wave.
- **UI legs against the existing ones.** The gates (`PLAYER_BAR_PROBE`, `PLAYER_NATIVE_PROBE`, `PLAYER_SMOKE_URL`), the player ids (`player.mpv`, `player.native`), `debug_seekProbe` (updated on every 0.5 s `refreshState`, so the Play Again leg sees the restart) and the reuse of `NativePlayerParityUITests.parse` all match the existing legs. The `hasFocus` loop presses Down up to three times. On a runtime that never reports `hasFocus`, the third press lands below the row and focus stays on poster 0, so the leg still holds. Apart from P2-2, the legs are consistent.
- **Unchanged paths.** The deep-link resume, local file, smoke rig default, Home resume cover and EpisodesSection's own cover all keep their behaviour when no pick is made: every new `onDismiss` returns at once on a nil pending.
